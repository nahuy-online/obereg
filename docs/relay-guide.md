# Внешний узел туннеля (референсный релей)

Клиентское приложение не обходит блокировки само по себе: локальный прокси ядра выпускает
трафик с того же устройства. Чтобы трафик выходил из другой сети, нужен внешний узел —
в репозитории есть референсная реализация: бинарник `obereg-relay` (крейт `obereg-relay`).

## Как это работает

```
оболочка (WebView / плеер)
      │  HTTP CONNECT / SOCKS5 на 127.0.0.1
      ▼
 локальный прокси ядра  ──► upstream: socks5 ──►  obereg-relay ──► цель (youtube.com и т.п.)
      (на устройстве)                                 (внешний сервер)
```

Ключевое: блокированный сетью участок — это отрезок «устройство → релей». Дальше запрос
идёт из сети релея, поэтому блокировка на стороне клиента его не касается.

## Запуск релея

```bash
# сервер вне зоны блокировок
cargo build --release -p obereg-relay
./target/release/obereg-relay \
  --listen 0.0.0.0:1080 \
  --journal /var/log/obereg-relay.jsonl \
  --status-file /var/run/obereg-relay.json
```

| Аргумент | Назначение |
|---|---|
| `--listen <addr>` | адрес прослушивания (по умолчанию `127.0.0.1:1080`) |
| `--journal <path>` | журнал событий в формате JSONL (`:memory:` — без записи) |
| `--status-file <path>` | файл со статусом: адрес, состояние, число обслуженных соединений, байты |
| `--print-config` | печатает готовую конфигурацию клиента и выходит |

## Подключение клиента

`obereg-relay --print-config --listen <адрес-релея>` печатает JSON; соответствующий
фрагмент конфигурации клиента:

```json
"tunnel": {
  "listen_addr": "127.0.0.1:0",
  "http_listen_addr": "127.0.0.1:0",
  "mode": "tunnel",
  "upstream": { "kind": "socks5", "addr": "<адрес-релея>" }
}
```

Проверено сквозным тестом `crates/obereg-relay/tests/relay_chain.rs`:
цель отвечает 200 через цепочку, релей считает обслуженное соединение,
локальный прокси клиента остаётся на `127.0.0.1`, а релей адресуется отдельно.

## Аутентификация (обязательна для публичного адреса)

Открытый прокси в интернете — это приглашение для чужих людей гонять через него трафик,
поэтому релей умеет требовать логин и пароль:

```bash
./target/release/obereg-relay \
  --listen 0.0.0.0:1080 \
  --user obereg --password «длинный-пароль» \
  --status-file /var/run/obereg-relay.json
```

Проверяются оба входа: SOCKS5 (RFC 1929) и HTTP CONNECT (Basic). Без учётных данных
HTTP-вход отвечает `407 Proxy Authentication Required` и соединение не обслуживается.

Клиент берёт данные из той же подсказки:

```json
"upstream": {
  "kind": "socks5",
  "addr": "<адрес-релея>:1080",
  "username": "obereg",
  "password": "<пароль>"
}
```

Проверено тремя тестами (`cargo test -p obereg-core --test tunnel_auth`): корректные
учётные данные пропускают трафик, отсутствие данных даёт 407 и ноль обслуженных соединений,
а локальный прокси без пароля продолжает работать штатно.

## Что в релее есть, а что предстоит

| Готово в референсе | Нужно для эксплуатации |
|---|---|
| SOCKS5-эндпоинт на публичном адресе | обфускация транспорта и устойчивость к DPI |
| Аутентификация: SOCKS5 (RFC 1929) и HTTP CONNECT (Basic) | лимиты скорости и объёма, квоты, биллинг |
| Журнал событий и файл статуса | мониторинг, алерты, метрики |
| Работа по `host:port`, поддержка аутентификации по логину и паролю | несколько узлов, ротация адресов, переключение на клиенте |
| Воспроизводимый запуск и тесты | — |

## Типовой порядок вывода узла

1. Поднять сервер вне зоны блокировок, запустить `obereg-relay` **с логином и паролем** (`--user/--password`).
2. Проверить снаружи: `curl -x socks5h://логин:пароль@<адрес-релея> https://api.ipify.org`
   должен вернуть адрес сервера.
3. Прописать адрес в конфигурации клиента (`upstream.kind = "socks5"`).
4. На телефоне открыть экран YouTube и убедиться, что строка маршрута показывает «через туннель»,
   а счётчик обслуженных соединений растёт.
5. Следить за `--status-file`: если соединения не растут, смотреть журнал релея.
