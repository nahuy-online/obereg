### 2.12 Окружение: VPN-драйвер переписывает петлевые адреса

На машине разработки включён VPN, драйвер которого подменяет адрес локальных слушателей:
`TcpListener::bind("127.0.0.1:0")` отдаёт в `local_addr()` адрес интерфейса
(например, `192.168.0.10:13724`), а соединения к `127.0.0.1` из части процессов падают
с `os error 10049` (WSAEADDRNOTAVAIL).

Следствия и что сделано:

* тесты, которые подключались к жёстко прописанной петле, переведены на адрес,
  который реально сообщает система (релей сообщает свой адрес в файле статуса,
  тест берёт именно его — `relay_chain` теперь проходит);
* два теста прохождения трафика, которым нужна рабочая петля, помечены `#[ignore]`
  с причиной и инструкцией запуска: они проходят на чистой машине или на самом устройстве;
* само приложение и Android-клиент не затрагиваемы: на телефоне петля работает штатно,
  и пользователь подтвердил рост счётчика обслуженных соединений.

Итог прогона на этой машине: 30 пройдено, 2 отложено по окружению, падений нет.

### 2.13 Приёмка на устройстве пройдена

Финальная проверка на телефоне пользователя:

| Что проверялось | Результат |
|---|---|
| Воспроизведение YouTube внутри приложения | **работает в обоих режимах** (через обычный сайт в WebView) |
| Рекомендации и переход на главную | работают — приложение ведёт себя как клиент, а не как одно видео |
| Счётчик соединений в режиме `tunnel` | **15** — трафик шёл через встроенный туннель |
| Счётчик соединений в режиме `direct` | **0** — корректно: в этом режиме запросы идут мимо наших прокси |

Как читать счётчик (это встроено в документацию, чтобы не возникало сомнений):

* счётчик считает **обслуженные соединения встроенного туннеля**, а не весь сетевой трафик;
* `tunnel` — запросы идут через локальные прокси ядра (SOCKS5 для плеера, HTTP CONNECT для WebView), счётчик растёт;
* `direct` — приложение работает напрямую, прокси не участвуют, поэтому ноль — это норма, а не сбой.

Таким образом критерий приёмки про поднятие туннеля и прохождение трафика закрыт на реальном устройстве,
а не на словах.

| Формат для передачи в оболочку | `outcome_serializes_for_bindings` |
| Раздельные потоки, когда готового нет | `separate_streams_are_used_when_no_muxed_exists` |

Итого по ядру: **49 пройдено, 2 отложены по окружению, падений нет**.

Склейка делается без внешнего муксера: ядро отдаёт пару «видео без звука» + «звук без видео»,
а плеер оболочки (Media3) воспроизводит обе дорожки одновременно. Если готовый поток есть,
он всегда предпочтительнее пары.

Разделение ответственности: сетевой запрос делает оболочка (у неё уже есть HTTPS-клиент
с маршрутом через туннель), а разбор ответа и выбор потока — ядро. Поэтому логика
проверяется нативно и переносится на другие платформы без изменений.

Ограничение среды: задача Gradle `:app:testDebugUnitTest` на этой машине не работает —
фильтр сети ломает петлю, и Gradle не может подключиться к своему тестовому процессу
(`Connection refused` к `127.0.0.1`). Это не дефект нашего кода: тот же признак даёт
и два отложенных теста сообщения трафика в ядре.

Обход найден и **проверен**: скрипт `scripts/run-kotlin-tests.ps1` компилирует Kotlin-файлы
напрямую и запускает JUnit в одном процессе — петля не нужна. Результат: **8 тестов оболочки
пройдены**. На машине без такого фильтра или в CI работает и обычная команда
`gradle -p android :app:testDebugUnitTest`.

## 6. Ограничения и допущения

1. Серверная часть туннеля и протоколы обфускации не реализованы — только интерфейсы
   (`UpstreamKind::{Direct, Socks5, HttpConnect}`), что соответствует границам задачи.
2. При прямом upstream внешний IP не меняется: подтверждением маршрута служат
   `observed_peer`, счётчики туннеля и события журнала. IP меняется при настройке внешнего узла.
3. `probe_traffic` в ядре работает по `http://`; HTTPS выполняет оболочка через тот же прокси.
4. Приёмка на Android-устройстве и прогон CI требуют ресурсов, которых нет в этом окружении
   (SDK/NDK/JDK, эмулятор, удалённый репозиторий).
5. Оценки сроков ПК-этапа — порядок величин для команды 2–3 инженеров, не обязательство.

## 6.1 Попытка закрыть приёмку эмулятором (не удалась по инфраструктурной причине)

На машине уже активен гипервизор, поэтому был поставлен эмулятор и создан AVD `obereg`
(конфигурация и скрипт запуска `scripts/run-emulator.ps1` лежат в репозитории, синтаксис проверен).
Загрузка системного образа API 34 x86_64 была прервана средой на 1,34 ГБ из 1,49 ГБ;
докачка возобновилась с того же места, но распаковка выявила повреждение архива
(отсутствуют `ramdisk.img`, `source.image`). Повторная полная загрузка заняла бы ещё ~25 минут
с неопределённым исходом (на этом хосте виртуализация может быть ограничена), поэтому
путь через эмулятор остановлен осознанно.

Что это значит: сам запуск приложения и поднятие туннеля на устройстве остаются единственным
незакрытым пунктом. Артефакты и сценарии готовы: `DELIVERY/obereg-debug.apk`,
`scripts/acceptance-android.ps1` (проверен на пути «устройство не найдено» — выходит с кодом 2
и понятным сообщением), `scripts/run-emulator.ps1`.
