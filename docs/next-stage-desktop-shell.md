# Следующий этап: ПК-оболочка (Windows и macOS) поверх готового ядра

Документ описывает, что переиспользуется без изменений, какие точки расширения нужны
и в каком порядке вести работы. Оценка — для команды из 2–3 инженеров.

## 1. Что переиспользуется без изменений

| Компонент | Почему готов |
|---|---|
| `obereg-core` целиком | Ядро не содержит платформенного кода: только `std`, `serde`, `serde_json`, `thiserror` |
| Транспортная прослойка (`transport`) | Сетевой код на `std::net`; одинаково работает на Windows и macOS |
| Туннельный движок (`tunnel::LoopbackTunnel`) | Локальный SOCKS5-прокси не требует драйверов и прав администратора |
| Журнал (`journal::FileJournal`) | JSONL на диске; путь задаёт оболочка (`%APPDATA%`, `~/Library/Application Support`) |
| Состояние и наблюдатели (`state`) | UI подписывается тем же способом, что и на Android |
| `obereg-ffi` (C ABI) | Уже собирается под Windows (`obereg_ffi.dll`) и macOS (`libobereg_ffi.dylib`) |
| `obereg-cli` | Готовый харнесс для проверки ядра и прогона `demo`/`bench` на ПК |

Итого: весь «дорогой» слой (ядро, туннель, инфраструктура, журнал) на ПК уже работает.
Требуется только оболочка.

## 2. Что нужно добавить

| # | Точка расширения | Зачем | Как реализуется |
|---|---|---|---|
| 1 | Плеер-адаптер | Воспроизведение видео на ПК | libmpv / mpv.net через отдельный адаптер; ядро отдаёт только потоки |
| 2 | Модель потоков | Единый формат качеств и кодеков | Уже описана в ядре; адаптеру нужно только её отрисовать |
| 3 | Настройка путей | Журнал и кэш по правилам ОС | `%APPDATA%\Obereg\journal.jsonl`, `~/Library/Application Support/Obereg/journal.jsonl` |
| 4 | Направление трафика в прокси | Чтобы плеер и API шли через туннель | Передать плееру адрес из `local_proxy_addr()`; libmpv умеет `--http-proxy=socks5://127.0.0.1:PORT` |
| 5 | Автообновление | Правки видеосервиса и волны блокировок | Канал обновлений + подпись кода (см. п. 4) |
| 6 | Единая подписка | Один платёж на все устройства | Требуется интерфейс лицензии в ядре — точка расширения, а не переписывание |
| 7 | Телеметрия живости | Единая схема событий | Использовать существующие `JournalKind`-события |

## 3. Отличия ПК, которые нужно учесть

| Аспект | Особенность | Решение |
|---|---|---|
| Распространение | Нет магазина: установщик + подпись | Сертификат подписи кода; накопление репутации в системе защиты Windows занимает время |
| macOS | Нотаризация | `codesign` + `notarytool`; без него — предупреждения при запуске |
| Системный VPN | Требует драйвера и прав администратора | Не делать: встроенный туннель работает без драйверов; системный VPN — опциональная точка расширения |
| Плеер | Другое ядро воспроизведения | Отдельный адаптер, ядро не меняется |
| Обновления | Обязательны | Автообновление с проверкой подписи |

## 4. Порядок работ и оценка

| Шаг | Работа | Оценка |
|---|---|---|
| 1 | Оболочка Windows: окно, список/поиск, плеер на libmpv, кнопка туннеля, экран журнала | 3–5 недель |
| 2 | Подпись, установщик, автообновление | 1–2 недели |
| 3 | macOS-оболочка (переиспользует 100% кода оболочки Windows, отличия — системные пути и нотаризация) | 2–3 недели |
| 4 | Сквозная проверка: `demo`-сценарий на ПК, baseline бенчмарка | 1 неделя |
| **Итого** | | **6–11 недель** |

При монолитной Android-разработке без разделения ядро/оболочка тот же результат стоил бы
5–8 месяцев: пришлось бы выковыривать извлечение контента и транспорт из Android-кода.

## 5. Критерии готовности ПК-этапа

1. Приложение запускает ядро и поднимает туннель без драйверов и прав администратора.
2. `local_proxy_addr()` направляется в плеер; трафик воспроизведения идёт через туннель.
3. Журнал пишется по системному пути и переживает перезапуск приложения.
4. Baseline бенчмарка на ПК зафиксирован и сопоставим с Android-значениями.
5. Установщик и обновление подписаны.
