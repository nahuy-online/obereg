# Бенчмарк инициализации ядра

## Что измеряем

Стоимость «холодного» пути, который видит пользователь при включении туннеля:

| Метрика | Что включает |
|---|---|
| `session_new_ms` | `CoreConfig::validate` + открытие журнала + инициализация роутера и движка |
| `tunnel_start_ms` | создание слушателя, запуск потока приёма, запись событий в журнал |
| `session_stop_ms` | остановка потока приёма, закрытие слушателя, финальные записи журнала |

`journal_path = ":memory:"` — измеряется вычислительная часть без дисковых операций.

## Методика

1. Один прогрев (первый запуск дороже: ленивая инициализация аллокатора, DNS-кэш).
2. `N` итераций: `new` → `start` → `stop`, каждая метрика замеряется `std::time::Instant`.
3. Считаются `min`, `p50`, `mean`, `p95`, `max` и число образцов.
4. Отчёт пишется в JSON (`obereg.bench/v1`) с ОС, архитектурой и версией API.

```bash
cargo run --release -p obereg-cli -- bench --iterations 30 --out bench/baseline.windows.json
```

Обязательно **release**-профиль: в debug-сборке числа не сопоставимы.

## Порог реакции

| Отклонение от baseline | Действие |
|---|---|
| до 20% | нормальный разброс, ничего не делать |
| 20–50% | разобраться, что изменилось; при обосновании — обновить baseline в том же PR |
| более 50% | блокирующая регрессия: разобраться до мёржа |

## Baseline

| Файл | Когда обновлять |
|---|---|
| `bench/baseline.windows.json` | локальный прогон на Windows (`scripts\bench.ps1`) |
| `bench/baseline.windows-ci.json` | генерируется job `bench` в CI, артефакт `bench-baseline` |

Числовые значения baseline фиксируются вместе с ОС, архитектурой и числом итераций —
иначе сравнение бессмысленно.
