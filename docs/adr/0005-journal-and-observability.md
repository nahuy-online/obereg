# ADR-0005: Журнал туннеля и наблюдаемость (JSONL на диске)

- Статус: принято
- Дата: 2026-09-22
- Контекст: [interfaces.md](../interfaces.md) §4, [module-registry.json](../module-registry.json) (`journal`)

## Контекст

Критерий приёмки MVP — `tunnel-event-journal`: события туннеля и сессии должны сохраняться и переживать перезапуск процесса. Журнал нужен и для отладки (что происходило с туннелем), и для проверки «трафик идёт через туннель» (проба с `via` и `observed_peer`). Среда — Android (оболочка читает файл или дергает FFI), CLI, позже ПК.

## Решение

Структурированный **JSONL на диске**, путь задаётся `CoreConfig::journal_path` (`None` → `MemoryJournal`). Append-only; каждая строка — один JSON-объект:

```json
{"ts_ms":1769040000000,"seq":42,"kind":"traffic_probe","session_id":"s-0x1f","message":"probe ok","fields":{"via":"tunnel","status":"204","observed_peer":"203.0.113.7:443"}}
```

| Поле | Тип | Семантика |
|---|---|---|
| `ts_ms` | `u64` | unix time, мс |
| `seq` | `u64` | монотонно растёт в пределах файла |
| `kind` | string | вариант `JournalKind`, snake_case |
| `session_id` | string | идентификатор сессии (обязательное поле) |
| `message` | string | человекочитаемое описание |
| `fields` | map<string,string> | структурированные данные события |

Покрытие событиями (все обязательные в MVP):

- старт/остановка/ошибка туннеля — `TunnelStart`, `TunnelStop`, `TunnelError`;
- переключение транспорта — `TransportSwitch` (`from`, `to`);
- запуск/остановка сессии — `SessionStart`, `SessionStop`;
- проба трафика — `TrafficProbe` (с `via` и `observed_peer`);
- изменение конфига — `ConfigChanged` (`source`).

Механика записи и чтения:

1. Пишущий поток один; `Journal::append` потокобезопасен (мьютексы записи и счётчика внутри `FileJournal`), возвращает назначенный `seq`.
2. Запись с `flush` + `sync_data()` после каждого события: событие переживает падение процесса.
3. `seq` восстанавливается при `open` как **максимум** валидных `seq` по файлу; повреждённая строка при чтении пропускается и не ломает журнал, `seq` берётся из последней целой.
4. Чтение — `Journal::read_all` возвращает всё (MVP, без пагинации), отсортировано по `seq`.
5. Ротация: при превышении **10 МБ** файл переименовывается в `journal.1.jsonl` (одна ротация, старый файл перезаписывается) — журнал остаётся читаемым руками и не растёт бесконечно.

Критерий приёмки: kill процесса в произвольный момент → перезапуск → `read_all` содержит все события до падения, `seq` продолжает монотонно.

Реализация в версии `0.1.0`: восстановление `seq` и `sync_data` есть; ротация >10 МБ и событие `ConfigChanged` из обработки конфигов — заявленный контракт, подлежащий доведению в коде (см. открытые вопросы в отчёте).

## Почему JSONL, а не SQLite

| Критерий | JSONL | SQLite |
|---|---|---|
| Зависимости ядра | нулевые | биндинг C-библиотеки в каждый тулчейн |
| Читаемость вручную | `cat`/`jq` на месте | нужен дамп |
| Парсинг оболочкой | построчно, тривиально | нужен драйвер на каждой платформе |
| Запись | append, дешёвый | журнал транзакций, fsync-логика своя |
| Запросы по журналу | не нужны в MVP | избыточны |

Нужны полноценные запросы по журналам — это отдельный ADR поверх того же трейта `Journal` (API `append/read_all` не меняется).

## Последствия

- Плюсы: ноль зависимостей, устойчивость к падению (fsync), деградация мягкая (повреждённый хвост отбрасывается), формат стабилен для парсеров.
- Минусы/ограничения: `read_all` в MVP читает весь файл (до 10 МБ) — приемлемо; полнотекстовый поиск и агрегации — на стороне оболочки; поля `fields` — строки (без вложенности).
