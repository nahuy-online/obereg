# ADR-0004: Стратегия FFI (ручной C ABI + JNI + Swift поверх C ABI)

- Статус: принято
- Дата: 2026-09-22
- Контекст: [architecture.md](../architecture.md), [interfaces.md](../interfaces.md)

## Контекст

Ядро Obereg написано на Rust (крейт `obereg-core`). Оболочки — Android/Kotlin (обязательно в MVP), iOS/Swift (пример), ПК-оболочка (план). Нужен механизм вызова ядра из Kotlin и Swift со стабильным контрактом, минимальной магией сборки и отладочным опытом, доступным одному разработчику на Windows-хосте.

Публичный API мал и стабилен: 10 функций C ABI + 8 методов JNI (см. §9 [interfaces.md](../interfaces.md)).

## Решение

Три слоя, строго друг на друге:

| Слой | Крейт/артефакт | Для кого | Что содержит |
|---|---|---|---|
| C ABI | `obereg-ffi` (`crate-type = ["cdylib", "staticlib"]`), заголовок `include/obereg.h` **пишется вручную** | Kotlin/JNI, Swift, CLI, любой FFI | `obereg_core_*`, `obereg_string_free`, коды ошибок |
| JNI | `obereg-jni` (только Android) | Android-оболочка | `app.obereg.core.CoreBridge`, трансляция `String`/`Long` ↔ C ABI |
| Swift | пример `apps/ios`, C ABI + module map | iOS | `OberegCore`, тонкая обёртка над `include/obereg.h` |

Правила владения памятью (контракт C ABI):

1. Хэндл ядра — непрозрачный указатель `OberegCore*`; перед каждым вызовом — null-check, `null` даёт код `-1`.
2. Строки возвращаются как выделенные Rust-аллокатором `CString`; освобождаются **только** через `obereg_string_free`; копирование в строку платформы — немедленно после возврата.
3. Ошибки — через код возврата (§9 [interfaces.md](../interfaces.md)) + текст в `obereg_core_last_error` (thread-local); варианты `CoreError` отдельными кодами не транслируются, исключения через FFI не выбрасываются.
4. `obereg_core_free` завершает жизнь хэндла; повторное использование — дефект вызывающей стороны, слой защиты — только debug-assert.

Заголовок `include/obereg.h` поддерживается вручную; CI-тест сверяет набор экспортируемых символов с реестром из `module-registry.json`, чтобы ручной заголовок не разошёлся с кодом.

## Альтернативы и причины отказа

| Альтернатива | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| UniFFI (Scaffolding/bindgen) | Автогенерация Kotlin/Swift биндингов, меньше ручного кода | Дополнительная тулчейн-зависимость и генерация в сборке; «магия» усложняет отладку JNI-крешей; для API из 10 функций выгода мала | Отклонено |
| flutter_rust_bridge | Удобно для Flutter-стека | Не наш стек (Kotlin/Swift нативные оболочки) | Отклонено |
| Expose Rust-типов напрямую (repr(Rust) в FFI) | Нулевой слой трансляции | Раскладка типов Rust не стабильна по определению; любая правка структуры ядра молча ломает ABI | Отклонено |

## Почему не expose Rust-типов напрямую

Единственная причина — стабильность ABI. Через границу идут только C-типы: `char*`, `int32_t`, непрозрачный указатель. JSON как формат обмена (`config_json`, `status`, `journal_read`) выводит эволюцию структур из-под контроля ABI: поля JSON добавляются с дефолтом без пересборки контракта.

## Последствия

- Плюсы: прозрачный стек вызовов (Kotlin → JNI → C ABI → Rust), отладка любым ABI-отладчиком, нет генерации в CI.
- Минусы: ручная синхронизация заголовка, JNI и ядра — компенсируется CI-тестом символов и контрактом в `interfaces.md`.
- Обратная совместимость FFI в пределах `MAJOR = 0` обязательна (см. ADR-0006).
