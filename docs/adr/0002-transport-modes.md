# ADR 0002. Транспортная прослойка с двумя режимами

- Статус: принято
- Дата: 2026-09-22
- Компонент: `obereg_core::transport`

## 1. Контекст

Туннель в Obereg — **опциональная** функция. Продукт обязан одинаково работать:

- в режиме «напрямую» (`Direct`), без туннеля;
- в режиме «через туннель» (`Tunnel`), с локальным прокси ядра и upstream.

Требования:

- Плеер и UI **не должны знать** о транспорте: они запрашивают соединение, а не выбирают маршрут.
- Отказ туннеля **не должен** превращать продукт в кирпич — нужен автоматический аварийный откат.
- Выбор режима по умолчанию может зависеть от региона/геолокации, но решение принимает **оболочка**
  и передаёт его ядру через конфиг; ядро геолокацию само не определяет.

## 2. Решение

Введён модуль `obereg_core::transport` — единственная точка, через которую в продукте устанавливаются
сетевые соединения.

### 2.1. Трейт `Transport`

```rust
pub trait Transport {
    fn name(&self) -> &'static str;
    fn mode(&self) -> TransportMode;
    fn probe(&self) -> Result<ProbeResult>;
    fn connect(&self, target: &str, port: u16) -> Result<Box<dyn Connection>>;
}
```

### 2.2. Реализации

| Реализация | Режим | Что делает |
|------------|-------|------------|
| `DirectTransport` | `Direct` | соединяется напрямую средствами ОС (`std::net`) |
| `TunnelTransport` | `Tunnel` | поднимает локальный прокси ядра и направляет трафик в upstream |

### 2.3. `TransportRouter`

`TransportRouter` — фасад транспортной прослойки. Держит активный режим и маршрутизирует вызовы.

- **Активный режим** хранится в роутере и меняется только через ядро (`set_transport_mode`).
- **Автоматический фолбэк `Tunnel → Direct`** при отказе туннеля: если `TunnelTransport` не может
  поднять прокси, не проходит `probe` или соединение падает, роутер переключается на `Direct` и
  фиксирует событие `TransportSwitch` в журнале. Продукт продолжает работать в режиме `Degraded`.
- **Умный дефолт по геолокации** задаётся оболочкой через конфиг: оболочка знает регион и выставляет
  начальный `TransportMode`. Ядро только применяет заданный дефолт и не выясняет регион само.

### 2.4. Изоляция от плеера

Плеер вызывает **только прослойку** (`TransportRouter::connect`). Плеер не имеет доступа к
`TunnelTransport`, к адресу локального прокси и к понятию «режим». Всё, что видит плеер, — успех или
ошибка соединения.

## 3. Обоснование

- **Опциональность туннеля** — продуктовое требование: туннель можно не включать и он не должен быть
  обязательным путём для трафика.
- **Аварийный режим** защищает от ситуации «туннель сломался — продукт умер». Отказ туннеля приводит к
  понижению до `Direct`, а не к отказу продукта.
- Единая точка соединений упрощает аудит: все сетевые выходы проходят через один модуль и логируются.
- Разделение ответственности: ядро умеет переключать режим, решение «какой режим по умолчанию в этом
  регионе» принимает оболочка.

## 4. Последствия

- Транспортные режимы и фолбэк версионируются вместе с `CORE_API_VERSION`.
- Оболочка обязана задать начальный режим (или принять дефолт ядра), иначе применяется безопасный
  дефолт `Direct`.
- Смена режима наблюдаема: `StateSnapshot` и `ConnectionState::{Connected,Degraded}` отражают факт
  фолбэка, журнал фиксирует `TransportSwitch`.

## 5. Рассмотренные альтернативы

| Альтернатива | Почему отклонено |
|--------------|------------------|
| Только туннель, без режима `Direct` | нарушает опциональность; при отказе туннеля продукт превращается в кирпич |
| Только `Direct`, туннель вне ядра | невозможно единое тестирование и единый журнал; логика расползётся по оболочкам |
| Выбор режима в плеере | плеер не должен знать о транспорте; размывает границу из ADR 0001 |
| Определение геолокации внутри ядра | ядро не должно обращаться к платформенным API и сети для самоопределения региона |
| Ручное переключение без автофолбэка | требует участия пользователя в аварийной ситуации, противоречит требованию устойчивости |
