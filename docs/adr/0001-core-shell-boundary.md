# ADR 0001. Граница «ядро / оболочка»

- Статус: принято
- Дата: 2026-09-22
- Компонент: `obereg-core` (Rust), оболочки Kotlin / Swift / десктоп

## 1. Контекст

Продукт Obereg — неофициальный медиаплеер со встроенным опциональным туннелем.
Целевые платформы: Android, iOS, Windows, macOS.
Команда маленькая (единицы разработчиков), бюджет времени на дублирование логики отсутствует.

Ключевые требования, влияющие на архитектуру:

- Логика (конфиг, состояние, транспорт, туннель, журнал, сессии) должна быть **одной на всех платформах**, чтобы не расходились поведения и багфиксы.
- Туннель — **опциональная** функция: продукт обязан работать без него.
- Кроссплатформенная логика должна быть тестируемой **без UI, без устройства и без сервера туннеля**.
- Плеер и UI не должны знать деталей сети и туннелирования.

## 2. Решение

Введено разделение на **платформонезависимое ядро** и **тонкие оболочки**.

| Слой | Что это | Технология | Ответственность |
|------|---------|-----------|-----------------|
| Ядро | crate `obereg-core` внутри cargo workspace | Rust | конфиг, состояние, транспорт, туннель, журнал, сессии, версия API |
| Bindings | генерация и сопровождение FFI-слоя | Rust + генератор | стабильная C-ABI поверх ядра, владение памятью, маппинг ошибок |
| FFI | сгенерированный C-интерфейс | C ABI | вызовы ядра из нативных языков |
| Оболочки | тонкие клиенты | Kotlin (Android), Swift (iOS), десктоп (Windows/macOS) | UI, плеер, разрешения ОС, точки системной интеграции |

Ядро **не содержит UI и не обращается к платформенным API**. Оболочка **не содержит бизнес-логики** —
она вызывает ядро и отображает состояние.

Подключение оболочек к ядру — через **FFI** (C ABI). Это минимальный общий знаменатель, поддержанный
всеми целевыми платформами.

## 3. Направление зависимостей

```
shell (Kotlin/Swift/desktop)
   └──> bindings
          └──> ffi
                 └──> core
```

Зависимости идут **только сверху вниз**. Обратное направление (`core → ffi`, `core → shell`,
`ffi → shell` и т. п.) запрещено. Ядро никогда не знает о существовании оболочки.

## 4. Правила запрещённых зависимостей ядра

Разрешённые зависимости ядра — **только**:

- `std`
- `serde`, `serde_json`
- `thiserror`

Явно запрещено в `obereg-core`:

| Запрет | Причина |
|--------|---------|
| `std::process` | ядро не запускает и не управляет процессами; только in-process логика |
| любые платформенные API (Android/iOS/Windows/macOS bindings) | платформенные вызовы допустимы только в оболочке/FFI |
| сетевые крейты: `tokio`, `reqwest`, `hyper`, `async-std` и т. п. | ядро не тянет рантайм и не диктует модель асинхронности; MVP — блокирующий `std::net` |
| UI-типы (любые GUI/рендеринг крейты) | ядро платформо- и UI-нейтрально |
| крейты, требующие системных драйверов/прав суперпользователя | ядро должно собираться и работать в песочнице и в тестах |

Зависимости ядра дополнительно ограничены манифестом workspace и проверяются на ревью: добавление
любого крейта сверх списка выше требует нового ADR.

## 5. Последствия

Положительные:

- Одна реализация логики на 4 платформы; поведение и багфиксы не расходятся.
- Ядро тестируется на CI без устройства, без UI и без внешнего сервера.
- Оболочки маленькие: их можно переписать/заменить, не задев логику.
- Туннель и транспорт изолированы в ядре и не протекают в плеер.
- Границы проверяемы статически (направление зависимостей) и линтером зависимостей.

Отрицательные / издержки:

- Нужен поддерживаемый FFI-слой и генератор bindings; это отдельная стоимость.
- Все обращения оболочки к ядру идут через границу — растущая поверхность API требует версионирования
  (`CORE_API_VERSION`).
- Ядро не может использовать платформенные оптимизации напрямую — только через конфиг/интерфейсы.

## 6. Рассмотренные альтернативы

| Альтернатива | Суть | Почему отклонено |
|--------------|------|------------------|
| UniFFI | генерация bindings из Rust по описанию интерфейсов | отклонено на этом этапе: добавляет кодогенерацию и рантайм-зависимости, усложняет сборку на 4 платформах при маленькой команде; границы проще удержать на явном C ABI. Может быть пересмотрено позже |
| KMP (Kotlin Multiplatform) | общий код на Kotlin/JVM + native | отклонено: не покрывает десктоп Windows/macOS тем же качеством, тянет JVM/GC в ядро, ядро перестаёт быть не-UI и легковесным; риск, что логика сети утечёт в платформенный слой |
| Серверное ядро | вся логика на сервере, оболочки — тонкие клиенты | отклонено: продукт обязан работать локально и без сети; серверная логика требует инфраструктуры, авторизации и создаёт точку отказа и приватностный риск; туннель уже сам по себе сетевой компонент — дублировать это сервером нельзя |
| Логика в каждом нативном слое | по реализации на платформу | отклонено: дублирование, расхождение поведения, невозможность единого тестирования при маленькой команде |
