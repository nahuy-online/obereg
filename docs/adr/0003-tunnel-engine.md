# ADR 0003. Туннельный движок MVP

- Статус: принято
- Дата: 2026-09-22
- Компонент: `obereg_core::tunnel`

## 1. Контекст

Туннель — опциональная функция Obereg. На MVP нужно получить **работающий и тестируемый** механизм
прохождения трафика, не заходя в продвинутые сетевые техники (обход DPI, обфускация, выбор
продакшн-протокола).

Ограничения:

- Продукт должен тестироваться **без внешнего сервера туннеля**.
- Нужно уметь проверять, что трафик реально проходит через туннель, сквозным тестом.
- Оболочки (в первую очередь Android) должны иметь простой способ направить трафик в туннель.
- Нельзя занимать системный VPN: конфликт «один VPN на систему», запрос системного разрешения,
  драйверы на ПК.

## 2. Решение

Введён модуль `obereg_core::tunnel`.

### 2.1. Трейт `TunnelEngine`

```rust
pub trait TunnelEngine {
    fn name(&self) -> &'static str;
    fn start(&self, cfg: &TunnelConfig) -> Result<TunnelHandle>;
    fn stop(&self) -> Result<()>;
    fn local_addr(&self) -> Option<String>;
}
```

### 2.2. Реализация MVP — `LoopbackTunnel`

- TCP-сервер на `127.0.0.1` (адрес и порт из `TunnelConfig::listen_addr`).
- Протокол: **SOCKS5 `CONNECT` без аутентификации** (no-auth).
- Входящее соединение из локального сокета форвардится на **настроенный upstream**.
- Таймауты: `handshake_timeout_ms` на установку соединения/рукопожатие, `idle_timeout_ms` на простой.

### 2.3. Абстракция `Upstream`

```rust
pub enum UpstreamKind {
    Direct,
    Socks5,
    HttpConnect,
}
```

| `UpstreamKind` | Смысл |
|----------------|-------|
| `Direct` | форвард напрямую (полезно для тестов и режима без вышестоящего прокси) |
| `Socks5` | форвард в вышестоящий SOCKS5-прокси |
| `HttpConnect` | форвард через HTTP `CONNECT` |

`UpstreamConfig { kind, addr, username, password }` задаёт цель и, при необходимости, учётные данные.

### 2.4. Границы этапа (out of scope)

- **Серверная часть туннеля** — только на уровне интерфейсов; реализации в MVP нет.
- **Обфусцированные протоколы** — только на уровне интерфейсов.
- Явно вне области этого этапа: **реальный обход DPI** и **выбор продакшн-протокола**.

Иными словами, MVP фиксирует абстракции (`TunnelEngine`, `Upstream`), а не конкретную схему обхода
блокировок.

## 3. Почему именно SOCKS5-совместимый локальный прокси

- **Тестируется без сервера**: `LoopbackTunnel` можно поднять в тесте и направить в него трафик.
- **Сквозная проверка прохождения трафика**: тест видит фактическое соединение через локальный прокси,
  а не «якобы работает».
- **Простая интеграция в оболочках**: Android-оболочка может направить трафик в локальный прокси через
  `java.net.Proxy(SOCKS)`, без системных разрешений и драйверов.
- **Локализация сетевой логики**: всё внутри `obereg_core::tunnel` на `std::net`, без сторонних
  сетевых крейтов.

## 4. Почему сознательно не используется системный VPN

| Свойство системного VPN (VpnService / NetworkExtension) | Последствие | Вывод |
|---------------------------------------------------------|-------------|-------|
| Занимает единственный системный VPN | конфликт «один VPN на систему» | не годится как обязательный механизм |
| Требует системного разрешения пользователя | усложняет запуск и UX | отказ на MVP |
| На ПК требует драйвера | установка и совместимость | отказ на MVP |

Системный VPN остаётся **точкой расширения** (в особенности на ПК), но **не входит в MVP**.

## 5. Последствия

- Туннель изолирован в одном модуле и наблюдаем через журнал (`TunnelStart`, `TunnelStop`,
  `TunnelError`) и состояние (`listen_addr`, счётчики байт).
- `local_proxy_addr()` ядра отдаёт оболочке адрес локального прокси — это единственная точка интеграции.
- Продакшн-протокол и обфускация требуют отдельных ADR и замены/дополнения реализации `TunnelEngine`
  без изменения трейта.

## 6. Рассмотренные альтернативы

| Альтернатива | Почему отклонено |
|--------------|------------------|
| Системный VPN (VpnService / NetworkExtension) как MVP | конфликт одного VPN, системные разрешения, драйверы на ПК |
| Свой бинарный протокол сразу в MVP | невозможно тестировать без сервера, нет совместимости с оболочками |
| Обфускация/обход DPI в MVP | вне области этапа; усложняет проверяемость, требует серверной части |
| Встраивание сетевого движка в оболочки | дублирование, расхождение поведения, нарушает ADR 0001 |
