# Changelog — Obereg

Формат основан на Keep a Changelog. Версионирование публичного API ядра —
SEMVER по `CORE_API_VERSION` при `CORE_API_MAJOR = 0` (см. `docs/adr/0006-api-versioning.md`).

## [0.1.0] — 2026-09-22

Первый каркас MVP.

### Добавлено
- Модуль каталога `catalog`: трейт `CatalogSource`, локальная реализация `LocalCatalogSource`,
  элемент `VideoItem` и демонстрационный каталог; 9 тестов, включая поиск без учёта регистра,
  соблюдение лимита и отказ на битом JSON.
- Каталог доступен через `CoreSession::catalog_search`, C ABI `obereg_core_catalog_search`
  и JNI `CoreBridge.catalogSearch` (проверено дымовым тестом на JVM).
- Android: экран каталога (поиск и список) и переход из него в плеер с выбранной ссылкой.
- Экран плеера (PlayerActivity, Media3/ExoPlayer) с маршрутизацией трафика через SOCKS5 ядра.
- Cargo workspace: `obereg-core`, `obereg-ffi`, `obereg-jni`, `obereg-cli`.
- Ядро: модули `error`, `config`, `journal`, `state`, `transport`, `tunnel`, `session`, `version`.
- Транспортная прослойка с режимами `direct`/`tunnel` и автоматическим откатом tunnel → direct.
- Туннельный движок MVP: `LoopbackTunnel` — локальный SOCKS5-совместимый прокси с абстракцией upstream
  (`direct`, `socks5`, `http_connect`).
- Журнал событий в формате JSONL на диске, переживающий перезапуск процесса.
- Публичный API `CoreSession`: `new/start/stop/status/set_transport_mode/journal/local_proxy_addr/probe_traffic`.
- FFI: C ABI (`obereg-ffi`, заголовок `include/obereg.h`) и JNI-обёртка (`obereg-jni`, `app.obereg.core.CoreBridge`).
- CLI-харнесс `obereg-cli`: `version`, `config-default`, `start`, `stop`, `probe`, `journal`, `demo`, `bench`.
- Тесты: unit + интеграционные (жизненный цикл, персистентность журнала, прохождение трафика через туннель,
  сырой SOCKS5-обмен, откат транспорта).
- Бенчмарк инициализации ядра с сохранённым baseline (`bench/baseline.windows.json`).
- Дымовой тест JNI-биндингов на JVM (`tools/jni-smoke`): проверяет тот же контракт,
  которым пользуется Android-оболочка, включая переключение режима и журнал.
- Нативные библиотеки под три ABI Android собраны локально (NDK r26d + cargo-ndk):
  `android/app/src/main/jniLibs/{arm64-v8a,armeabi-v7a,x86_64}/libobereg_{jni,ffi}.so`.
- APK Android-оболочки собран локально и проверен: `app.obereg.player`, minSdk 26, targetSdk 34,
  10 553 376 байт, `native-code: arm64-v8a, armeabi-v7a, x86_64`.
- Сценарий приёмки одной командой: `scripts/acceptance-android.ps1` (установка, запуск сервиса,
  ожидание `tunnel_start`, выгрузка журнала, проверка переживания перезапуска).
- Скрипт запуска эмулятора для приёмки: `scripts/run-emulator.ps1` (headless AVD, ожидание загрузки).
- Экран плеера (PlayerActivity, Media3/ExoPlayer): воспроизведение видеофайла с
  маршрутизацией через локальный SOCKS5-прокси ядра (OkHttp data source).
  Первый прогон сборки доработал состав зависимостей; APK вырос с 10,1 до 15,3 МБ.
- Экран приёмки переработан: автотест одной кнопкой, живой журнал ядра на экране,
  явный вывод исключений вместо молчаливого отказа, автозапуск туннеля при открытии.
- Исправлена кодировка PowerShell-скриптов: файлы перезаписаны в UTF-8 с BOM, иначе
  Windows PowerShell читал кириллицу как ANSI и скрипты не парсились.

### Известные ограничения
- Протоколы обфускации и серверная часть туннеля — только на уровне интерфейсов (out of scope MVP).
- `probe_traffic` в ядре работает по `http://`; `https` выполняет оболочка через локальный SOCKS5-прокси ядра.
- Системный VPN (`VpnService`/`NetworkExtension`) не используется: туннель встроен в сетевое взаимодействие приложения.

### Прочее
- Добавлен референсный **внешний узел туннеля** — крейт `obereg-relay`:
  SOCKS5-эндпоинт на публичном адресе, журнал, файл статуса, подсказка конфигурации клиента
  (`--print-config`). Сквозной тест `crates/obereg-relay/tests/relay_chain.rs` поднимает
  релей отдельным процессом и проверяет цепочку клиент → локальный прокси → релей → цель.
- Туннель научился второму входу: к SOCKS5 добавился **HTTP CONNECT-прокси** —
  без него WebView (и любой браузерный движок) не может ходить через туннель.
  Адрес отдаётся через `CoreSession::local_http_proxy_addr`, C ABI
  `obereg_core_local_http_proxy_addr` и JNI `CoreBridge.localHttpProxyAddr`.
- Экран YouTube направляет трафик WebView в HTTP-прокси ядра через `ProxyController`
  (androidx.webkit); если туннель не поднят или Android младше 9 — идёт напрямую
  и честно пишет об этом в статусе.
- Тест `tests/http_proxy.rs`: `CONNECT` → ответ 200 → HTTP-запрос по туннелю →
  счётчики трафика и запись адреса в журнал.
- По итогам проверки на реальном устройстве исправлено:
  * тестовые ссылки в каталоге заменены — прежний бакет Google отдаёт 403, из-за чего
    плеер показывал чёрный экран; теперь источники проверены и добавлено встроенное
    видео `assets/sample.mp4` для проверки плеера без сети;
  * в плеере выводится ошибка воспроизведения и состояние плеера (раньше отказ был молчаливым);
  * плеер использует `DefaultDataSource`, поэтому играет и локальные файлы, и сетевые;
  * автотест больше не запускает уже запущенную сессию (раньше показывал ошибку
    «session is already running») и печатает прирост обслуженных соединений.
- Подтверждено на устройстве: режим tunnel, локальный прокси, счётчики трафика растущие
  (6 953 Б / 35 126 Б, 7 соединений) — туннель работает на телефоне.
- Baseline бенчмарка пересчитан после добавления каталога: p50 создания сессии 0,004 мс,
  поднятия туннеля 0,109 мс, остановки 0,108 мс (30 итераций + прогрев).
- Итоговый HTML-отчёт (`DELIVERY/obereg-mvp-handoff.html`) перегенерирован: предыдущая
  редакция была испорчена ошибочной массовой заменой при правке документов.
- README дополнен методами каталога; в `tools/jni-smoke/README.md` добавлены результаты
  проверок каталога; все PowerShell-скрипты перезаписаны в UTF-8 с BOM.

### Исправлено после независимого ревью (2026-09-22)
- Дисциплина блокировок: `handle` больше не удерживается во время сетевых операций
  и уведомления наблюдателей — исключён сценарий самоблокировки, когда UI-наблюдатель
  вызывает `status()` внутри колбэка.
- Автооткат `tunnel → direct` теперь меняет активный режим на фактический, пишет
  `transport_switch` в журнал, считает отказы (`fallback_count`) и передаёт причину
  наружу — состояние больше не может сообщать `tunnel`, когда трафик идёт напрямую.
- Туннель отслеживает активные клиентские соединения и закрывает их при остановке:
  раньше клиентские потоки жили до истечения таймаута простоя.
- Half-close при завершении потока: короткие ответы больше не ждут таймаута
  (проба через туннель ускорилась с 10 000 мс до 18 мс).
- SOCKS5-сервер корректно обрабатывает `nmethods = 0`, различает коды ответа
  (refused / unreachable), а лёгкая проверка туннеля проверяет выбранный метод аутентификации.
- Запись стартового события туннеля стала best-effort: сбой журнала не отменяет
  уже удавшийся запуск.
